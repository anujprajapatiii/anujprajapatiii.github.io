# Architecture Conventions

## Rules

- Use `@/` imports for source files. The alias maps to `./src/*`.
- Prefer `.astro` components for static and server-rendered UI.
- Use React only for stateful UI and client interactivity that genuinely
  needs it.
- Content collections are defined in `src/content.config.ts`.
- Public pages query content through `src/lib/content/queries.ts`. Keep direct
  `getCollection()` calls, publication filtering, sorting, and curation rules
  inside that layer.
- Filter drafts before rendering public listings.
- Site-wide facts (name, nav, social links) live in `src/data/site-config.ts`.
- Do not edit `dist/` as source. It is generated by `pnpm build`.

## Interactive Demo Boundary

Interactive experiments use two shared React layers:

- `src/components/ui/` contains controlled, accessible interaction primitives
  such as buttons, tabs, segmented controls, switches, sliders and tooltips.
  These components own semantics, keyboard/pointer behaviour and common visual
  states. They know nothing about experiments or content routes.
- `src/components/demo/` contains the responsive `DemoShell`/`DemoStage`
  composition plus the guided `DemoPanel`, `DemoStepList`, `DemoStepDetail`,
  `DemoSetting` and `DemoPanelFooter`. These components own structure,
  semantics and density, not experiment state.

The default panel is a guided explanation, not a developer dashboard. Raw
state, event history, playback controls and code belong behind an explicit
optional disclosure only when the experiment genuinely needs them. Stage
status badges are opt-in for meaningful visitor-facing status, never default
canvas chrome.

The experiment component remains the single source of truth for domain state,
timers and data. It passes controlled values and callbacks down through the
demo compositions into UI primitives. Astro continues to own the route,
metadata, prose and static page shell.

## Layout Hierarchy

- `BaseLayout.astro`: the HTML document — head, SEO, theme bootstrapping
- `PageLayout.astro`: the site chrome — header, main slot, footer

Add specialized layouts (e.g. a case-study layout) as children of
`PageLayout` when a content type needs its own shell.
